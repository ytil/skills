Делегируй. Проверяй. Приземляй.

Оркестратор долгой многоэтапной работы не пишет код сам — этапы выполняет внешний агент. Скилл делает такое делегирование безопасным: промпт этапа настолько точен, что работа возвращается правильной, а проверка настолько строга, что результат не страшно класть в main. Внешний агент способный, но заявляет больше, чем сделал, молча меняет поведение и, упёршись в лимит, останавливается без доклада. Опора оркестратора — скептицизм и проверяемые машиной доказательства.

Режим 1 · Автор

Предстоит поручить этап: синхронизироваться с remote и написать самодостаточный промпт этапа с обязательным worktree.

Режим 2 · Проверка

Пришёл отчёт: до коммита доказать его или опровергнуть. Это главный режим — отчёт лишь заявление, а не доказательство.

Ритм итерации
git pull→ поручить этап→ проверить→ приземлить→ git push→ ↻ следующий этап

Pull и push забываются легче всего, и у каждого пропуска своя цена: устаревшая база оборачивается merge-конфликтами при приземлении, а незапушенный этап невидим для CI и для всех, кто работает от remote. Когда приземлён последний этап — это ещё не «готово»: впереди финальный аудит приёмки (внизу страницы).

Один этап: от pull до push

две дорожки

Слева, бирюзовым — ветка main и действия оркестратора. Справа, медным — отдельный worktree, в котором работает внешний агент. Медная ветка ответвляется в момент поручения этапа и вливается обратно только после полной проверки.

main · оркестратор worktree · внешний агент
Шаг 1 · Синхронизация

Подтянуть remote

git pull целевой ветки до написания промпта. Удалённая ветка могла уйти вперёд, а этап, начатый от устаревшей базы, расплатится за это конфликтами при приземлении.

Шаг 2 · Промпт этапа

Промпт — это весь контракт

  • Что прочитать заранее — точными ссылками: разделы плана, файлы-образцы.
  • Порядок работ: по одной сущности за раз, полный набор проверок зелёный после каждого пункта.
  • Условия остановки вместо догадок: наткнулся на непредусмотренное — остановись и доложи, не выдумывай.
  • Чего не делать: файлы и работы, отложенные на следующие этапы, названы явно.
  • Отчёт в проверяемом виде: что нельзя проверить grep-ом, тому нельзя и верить.
→ references/stage-prompt.md

Контракт worktree: агент обязан создать отдельный git worktree, править только в нём и первой строкой отчёта назвать его абсолютный путь. Если создать worktree не удалось — остановиться и доложить.

git worktree add --detach
Шаг 3 · Реализация

Агент выполняет этап

Все правки — только внутри worktree, без веток и коммитов. Проверки зелёные после каждого пункта плана; если условие плана не выполняется — остановка и доклад, а не правдоподобная выдумка. Большой этап можно сдать частично: зелёный кусок плюс список того, что осталось.

Шаг 4 · Отчёт

Возвращается отчёт

Первой строкой — абсолютный путь worktree и базовый коммит; дальше — что стало с каждой сущностью, какие тесты изменились и почему, согласованные отклонения, сработавшие остановки. Без пути и базы отчёт неполон — иначе есть риск проверить не то дерево.

Шаг 5 · Проверка

Проверка — в worktree агента

  • Полный набор проверок — в фоне (pnpm qa или аналог из gate-playbook); ревью идёт параллельно с ним.
  • Оценить масштаб диффа: от него зависит глубина ревью. Новые файлы смотри отдельно — git diff их не показывает.
  • Состязательное ревью: искатели по направлениям, на каждую находку — опровергатель (схема ниже).
  • Ключевые утверждения отчёта проверь машиной сам: grep по имени символа с учётом алиасов и без тестов; SQL — скомпилировать и сравнить, а не читать; схемы — выгрузить и сравнить скриптом; «гейты эквивалентны» — негативный тест.
  • Свести результаты: находки, пережившие опровержение, плюс твои собственные. Твой grep весомее мнения агента; спор двух агентов решается чтением кода.

Разведка агента галлюцинирует: «ссылок нет» и «полностью удалено» в отчёте — лишь заявления. Каждое «удалено / перенесено / эквивалентно» проверяется машиной.

Развилка

Ошибка в деталях — или в самом подходе?

подход

Блокер в замысле (не тот слой, выдуманный контракт, неверно прочитанный план) — не латать. Worktree в сторону, решение принять самому и поручить этап заново новым промптом ↺ к шагу 2.

детали

Ошибки точечные — чинятся. Дальше по циклу.

Оркестратор остаётся рецензентом и коммитером: механические правки он выносит из своего контекста — тот же принцип «поручи, потом проверь».

Шаг 6 · Правки

Правки — субагенту, когда он есть

Весь подтверждённый список — файл, строка, доказательство, суть правки — отдаётся одному субагенту; правки вносятся в тот же worktree, где шли проверки и ревью. Если субагентов нет (Codex) — правь сам по зафиксированному списку, не пересматривая находки по ходу. Чинится всё, включая мелочи: отложенная мелочь просто всплывёт снова через этап.

Шаг 7 · Проверки заново

Полный прогон после правок

Любая правка обнуляет прежний зелёный результат. Типичная ошибка — закоммитить после правок, прогнав один только typecheck: зелёный typecheck не означает зелёные knip и format.

git cherry-pick <sha>
Шаг 8 · Приземление

Перенести работу на main

  • Сначала git pull на main: пусть конфликты всплывут, пока результаты проверок ещё свежие, а не в момент push.
  • Коммит делается внутри worktree: git -C wt add -A && git -C wt commit — простой diff | apply молча потерял бы новые файлы.
  • git cherry-pick <sha> в основную копию: база объектов у worktree общая, коммит виден из main.
  • Если база успела уехать, cherry-pick — это настоящее трёхстороннее слияние: полный прогон проверок на main заново и перепроверка утверждений по задетым файлам.
  • Всё зелёное — git worktree remove.
Шаг 9 · Push и память

Отправить и записать выводы

Один коммит на этап: что сделано, что исправлено после ревью, известные временные сбои. git push до начала следующего этапа — копить незапушенные этапы значит ставить при итоговом push всё на одну карту. Если push отклонён: git pull --rebase, разрешить конфликты, полный прогон проверок (перебазирование — такая же правка, как любая другая), снова push. В память проекта — хеш коммита и найденные подводные камни.

Состязательное ревью

шаг 5.3

По одному искателю на каждое независимое направление проверки; каждую найденную проблему — включая мелкие — атакует отдельный опровергатель, чья задача — доказать, что проблемы нет. Конвейер без общего барьера: находки одного направления уходят на проверку сразу, не дожидаясь остальных.

Масштаб по запросу: направления берутся из того, что этап реально менял, а не из фиксированного списка. Ревью — широкая сеть, но оно не заменяет твоих собственных машинных проверок. Метод один (review-workflow.md), механика исполнения у каждой среды своя:

Claude Code · review-runtime-claude.md

Полная форма метода. Скрипт Workflow: искатели и опровергатели — параллельные изолированные агенты, не знающие друг о друге; формат ответа проверяется на уровне инструмента, невалидный ответ перезапрашивается сам; проверки идут в фоне одновременно с ревью.

Codex · review-runtime-codex.md

Упрощённый путь. Сначала полный прогон проверок; направления — по одному, каждое заново от реального диффа; список находок фиксируется до их проверки; опровержение — отдельным запуском codex exec, где это возможно; JSON проверяешь сам. Компенсация — больший вес собственных машинных проверок.

Три принципа, на которых стоит цикл

выстрадано
I

«Обе проверки зелёные» — не эквивалентность

Зелёный результат на чистом коде говорит лишь, что сейчас ни одна проверка не срабатывает. Эквивалентность доказывает негативный тест: внести нарушение, убедиться, что его ловят оба механизма — старый и новый, — и откатить.

II

Разведка галлюцинирует — проверяй grep-ом по символу

Агент уверенно доложит «файл удалён, ссылок нет» — и ошибётся: искал по относительному пути, а импорт шёл через алиас. Утверждения «ссылок нет» проверяются только grep-ом по имени символа с учётом алиасов; код, живой только в тестах, ловится отдельно — grep -v '\.test\.'.

III

Находка не считается реальной, пока не пережила опровержение

Правдоподобная находка — ещё не настоящая. Независимый опровергатель на каждую пытается доказать обратное: настоящие дефекты выживают, остальное отбрасывается или понижается в серьёзности. Иначе правильный код «чинится» в неправильный.

Параллельные этапы

приземление по одному
Приземления — строго по одному. Несколько этапов в своих worktree от одной базы — нормально, но шаги 8–9 выполняются по очереди: этап A приземляется целиком, только потом B.
После каждого приземления базы остальных устаревают. Их проверки и ревью выполнялись против старой базы: когда придёт их очередь, полный прогон проверок на main обязателен, плюс перепроверка утверждений по файлам, которые задело предыдущее приземление.
Защита на этапе постановки: непересекающиеся наборы файлов. Если два параллельных этапа трогают один модуль — на самом деле это был один этап: объедини их или выстрой последовательно, а не устраивай гонку приземлений.

Финальный аудит приёмки

завершение работы

Последний этап приземлён — это ещё не «готово», это лишь «все этапы зелёные». Поэтапная проверка доказала, что каждый этап сделал написанное в его промпте; но никто пока не доказал, что промпты вместе покрывают исходную задачу. Дыры живут именно в этом шве: требования, которые не взял на себя ни один этап; планка качества, которую «держал кто-то другой»; мелочи, отложенные на этап, которого так и не случилось.

1 · Требования Вернуться к исходной постановке. К первоисточнику — документу, плану, словам пользователя, — а не к карте этапов: именно при её составлении объём работы незаметно сужается. Требования выписать явным чек-листом.
2 · Ревью полноты Та же машинерия — по всей работе целиком. Состязательное ревью по git diff <база работы>..HEAD с направлениями полноты:
requirements-coveragescope-fidelityquality-bardeferred-residue
3 · Машинная приёмка Прогнать поведение от начала до конца. Доказательства вместо пересказа: зелёные проверки говорят о здоровье кода, но не о том, что требование выполнено.
4 · Список пробелов Каждый пробел — новый этап или согласованное исключение. Подтверждённый пробел становится либо новым этапом (назад в режим автора), либо записанным исключением, которое пользователь явно одобрил. Готово — когда список пуст или согласован целиком.
