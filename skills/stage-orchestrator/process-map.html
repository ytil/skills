skill · stage-orchestrator · карта процесса

Делегируй. Верифицируй. Приземляй.

Оркестратор длинного многоэтапного рефакторинга не пишет код сам — этапы выполняет внешний агент. Скилл делает делегирование безопасным: промпт настолько точный, что работа возвращается правильной, и верификация настолько жёсткая, что за результат можно поставить main. Внешний агент способный, но переобещает, молча меняет поведение и замолкает на лимитах. Рычаг оркестратора — скептицизм плюс машинно-проверяемые доказательства.

Режим 1 · Author

Предстоит делегировать этап: синхронизироваться, написать самодостаточный stage-промпт с контрактом worktree.

Режим 2 · Verify

Пришёл отчёт: доказать или опровергнуть его до коммита. Несущий режим — отчёт это заявление, не доказательство.

Ритм итерации
git pull→ делегировать→ верифицировать→ приземлить→ git push→ ↻ следующий этап

Pull и push — два шага, которые забываются легче всего, и у каждого пропуска есть цена: устаревшая база оборачивается merge-конфликтами при приземлении, а незапушенный этап невидим для CI и для всего, что базируется на remote. Когда лёг последний этап — не «готово», а финальный аудит приёмки (внизу страницы).

Один этап: от pull до push

swimlane

Две дорожки: петролевая — main и действия оркестратора, медная — detached worktree, где работает внешний агент. Ветка отрастает при делегировании и вливается обратно только после полной верификации.

main · оркестратор worktree · внешний агент
Шаг 1 · Sync

Синхронизация с remote

git pull целевой ветки перед авторингом. Remote мог уйти вперёд — этап, построенный от устаревшей базы, расплатится за это при приземлении.

Шаг 2 · Author

Stage-промпт — весь контракт

  • Read-first по точным ссылкам: секции плана, файлы-образцы.
  • Порядок работ: по одной сущности, гейт зелёный после каждого юнита.
  • СТОП-условия вместо догадок: неизвестное превращается в решение оркестратора.
  • «Что НЕ делать» — отложенные файлы и этапы названы явно.
  • Отчёт в формате для верификации: то, что нельзя проверить grep-ом, нельзя и доверять.
→ references/stage-prompt.md

Контракт worktree: агент обязан создать отдельный detached git worktree, править только в нём и назвать его абсолютный путь в отчёте. Не может — СТОП.

git worktree add --detach
Шаг 3 · Implement

Агент реализует этап

Все правки — только внутри worktree, без веток и коммитов. Гейт зелёный после каждого юнита; на непокрытой предпосылке — СТОП и доклад, а не правдоподобная выдумка. Для большого этапа допустим зелёный частичный срез с картой остатка.

Шаг 4 · Report

Отчёт возвращается

Первой строкой — абсолютный путь worktree и base commit; затем карта per-entity, именованные дельты тестов, санкционированные отклонения, встреченные СТОПы. Без пути и базы отчёт неполный — не верифицировать чекаут оркестратора по ошибке.

Шаг 5 · Verify

Верификация — против worktree

  • Полный гейт в фоне в worktree (pnpm qa или аналог из gate-playbook) — ревью идёт параллельно.
  • Инвентаризация диффа: масштаб калибрует глубину; untracked-файлы отдельно — git diff их не показывает.
  • Адверсариальное ревью Workflow-ом: finders → verifiers (схема ниже).
  • Машинная проверка claims самому: grep по имени символа (alias-aware, минус тесты), компиляция SQL вместо чтения, дамп и diff схем, негативный тест для «гейты эквивалентны».
  • Реконсиляция: выжившие находки в их итоговой severity + собственные находки. Свой grep бьёт мнение агента; спор двух агентов решается чтением кода.

Разведка галлюцинирует: «0 refs» и «fully removed» в отчёте — это заявления. Каждое «удалено / мигрировано / эквивалентно» проверяется машиной.

Развилка

Подход верен — или только исполнение?

нет

Блокер в самом дизайне (не тот слой, выдуманный контракт, неверно прочитанный план) — не латать: выбросить worktree, принять решение самому и ре-делегировать этап новым промптом ↺ к шагу 2.

да

Детали поехали — чинится. Дальше по циклу.

Оркестратор остаётся ревьюером и коммитером: механические правки — вне его контекста, зеркаля тот же split «делегируй → проверь».

Шаг 6 · Fix

Фиксы — через субагента, если runtime его имеет

Весь подтверждённый набор — файл, строка, доказательство, замысел фикса — одному fix-субагенту, правки в том же worktree, где гонялись гейт и ревью. Без субагентов (Codex) — правишь сам по замороженному набору, не пересматривая находки в процессе. Чинится всё, включая миноры: отложенный минор просто переоткроется этапом позже.

Шаг 7 · Re-gate

Полный гейт заново

Любая правка переоткрывает гейт. Классическая рана — закоммитить после фикса, прогнав только typecheck: зелёный typecheck ≠ зелёные knip и format.

git cherry-pick <sha>
Шаг 8 · Land

Приземление на main

  • Сначала git pull на main — конфликты должны всплыть, пока свидетельства гейта свежие, а не при push.
  • Коммит внутри worktree: git -C wt add -A && git -C wt commit — голый diff | apply молча теряет untracked-файлы.
  • git cherry-pick <sha> в чекаут оркестратора — object database общая.
  • База уехала → это настоящий three-way merge: полный гейт на main заново и перепроверка claims по затронутым файлам.
  • Зелено → git worktree remove.
Шаг 9 · Push

Push, коммит-месседж, память

Один коммит на этап: что сделал этап, что починили после ревью, известные transient-ы. git push до старта следующего этапа — стопка незапушенных этапов превращает итоговый push в ставку на всё сразу. Push отклонён → git pull --rebase, резолв, полный гейт (ребейз — такая же правка), push. В память проекта — хеш коммита и выученные gotchas.

Адверсариальное ревью

workflow · шаг 5.3

Один finder на независимое измерение диффа; каждую находку — включая миноры — атакует отдельный verifier, чья работа — опровергнуть. Pipeline, не barrier: находки измерения верифицируются, как только его finder вернулся.

Масштаб под запрос: измерения выбираются из того, что этап реально трогал, а не из фиксированного списка. Ревью — широкая сеть, не замена собственным machine-check-ам поверх. Метод общий (review-workflow.md), механика исполнения — своя на runtime:

Claude Code · review-runtime-claude.md

Полная форма метода. Workflow-скрипт: finders и verifiers — параллельные изолированные агенты, слепые друг к другу; JSON-контракт валидируется на уровне tool-call (кривой ответ ретраится сам); гейт крутится в фоне параллельно ревью.

Codex · review-runtime-codex.md

Деградационный путь. Гейт первым и до конца; измерения по одному с пере-выводом из реального диффа; находки замораживаются до верификации; refuter-проход — отдельным codex exec, где возможно; JSON валидируешь сам. Компенсация: больший вес собственным machine-check-ам.

Три принципа, на которых стоит цикл

выстрадано
I

«Оба гейта зелёные» ≠ эквивалентность

Зелёный на чистом коде доказывает лишь, что ни один гейт не срабатывает сейчас. Доказательство эквивалентности — негативный тест: внести нарушение, убедиться, что ловят оба механизма, откатить.

II

Разведка галлюцинирует — grep по символу

Агент уверенно доложит «файл удалён, ссылок нет» — и ошибётся, потому что grep-ал относительный путь, а импорт шёл через alias. Claims о достижимости — только grep по имени символа, alias-aware, с grep -v '\.test\.' для test-only-live.

III

Находки подтверждаются адверсариально

Правдоподобная находка — не реальная. Независимый verifier на каждую пытается её опровергнуть: реальные дефекты выживают, остальное отбрасывается или понижается — и «правильное» не «чинится» в неправильное.

Параллельные этапы

landings serialize
Приземления — строго по одному. Несколько этапов в своих worktree от одной базы — нормально, но шаги 7–9 сериализуются: land A целиком, потом B.
После каждого приземления базы остальных устаревают. Их гейты и ревью были относительны старой базы: на их очереди re-gate на main обязателен, плюс перепроверка claims по файлам, которые тронуло раннее приземление.
Author-защита: непересекающиеся file sets. Два in-flight промпта трогают один модуль — значит это был один этап: слить или выстроить последовательно, а не гонять наперегонки.

Финальный аудит приёмки

closing the effort

Последний этап лёг — это не «готово», это «все этапы зелёные». Попэтапная верификация доказала, что каждый этап сделал то, что было в его промпте; никто ещё не доказал, что объединение промптов покрывает исходную задачу. Дыры живут в этом шве: требования, которых не заявил ни один этап, планки качества, которые «держал кто-то другой», миноры, отложенные на этап, которого не случилось.

1 · Требования Воскресить исходную задачу. Вернуться к первоисточнику — документ, план, слова пользователя, — а не к карте этапов: именно при её выводе скоуп незаметно сузился. Требования — в явный чек-лист.
2 · Адверс-ревью полноты Та же машинерия, дельта всего усилия. Ревью по git diff <effort-base>..HEAD с измерениями полноты:
requirements-coveragescope-fidelityquality-bardeferred-residue
3 · Машинная приёмка Прогнать поведение end-to-end. Доказательства вместо нарратива: зелёные гейты доказывают здоровье кода, а не то, что требование выполнено.
4 · Gap-лист Каждая дыра — этап или санкция. Подтверждённая дыра становится новым этапом (назад в Author) или явно записанным исключением, подписанным пользователем. Готово — когда список пуст или целиком санкционирован.
